## Цель

Доработать пайплайн хронометража транспортировки торфов:

1. Формировать отчёт **ежечасно в окне 6:00–22:00** (17 прогонов/день).
2. Добавить **пояснительную записку** — связный текст по итогам дня, генерируемый
   моделью через SSH-мост к Claude Code (тот же приём, что в проекте Geol), с
   детерминированным запасным вариантом «по правилам».
3. Добавить **алерты в Telegram** — о сбоях пайплайна и об аномалиях KPI.
4. Временно слать письма **только на `alexeimvc@gmail.com`** (остальных получателей
   сохранить закомментированными).

Принцип: ни одна новая часть не должна ломать существующий отчёт. Мост и алерты —
best-effort; сбой моста или Telegram не прерывает сборку XLSX/PDF.

**Новый поток `run_daily.py`:** `fetch → consolidate → build_pdf → explain →
(алерты об аномалиях) → notify_bot`. Алерты о сбоях шага отправляются в точке сбоя
(до раннего выхода). Шаг `explain` идёт после `build_pdf`, т.к. читает
`state/last_metrics.json`.

## Часть 2. Пояснительная записка через мост

### 2.1 Модуль `llm.py` (новый)

Копия моста из Geol, минимально необходимая поверхность:

- `available() -> bool` — есть ли SSH-ключ.
- `ask(prompt: str, timeout: int | None = None) -> str` — `ssh … "claude -p"`,
  промпт в **stdin** (не аргументом — иначе упираемся в ARG_MAX). Бросает
  `RuntimeError` при недоступности ключа/ненулевом коде.

Конфиг через env с дефолтами (значения уже известны, в код зашиты как умолчания):
`EU_CLAUDE_SERVER=185.200.179.31`, `EU_CLAUDE_USER=root`,
`EU_CLAUDE_KEY=~/.ssh/eu_claude`, `EU_CLAUDE_TIMEOUT=300`. Добавить эти ключи в
`.env.example` с комментарием. Зависимости — только стандартная библиотека.

### 2.2 Метрики из `build_pdf.py`

`build_pdf.py` в конце `main()` дополнительно сохраняет компактный
`state/last_metrics.json` (переиспользуя уже посчитанные DataFrame'ы). Состав:

- `report_date`, `period` (min/max дат);
- итоги: `total_volume`, `total_trips`, `m3_per_trip`, `n_drivers`, `n_trucks`,
  `n_units`;
- `by_unit`: список {подразделение, рейсы, объём, м³/рейс, доля_%};
- `by_date`: список {дата, объём, рейсы} (для динамики день-к-дню);
- `truck_util`: средняя загрузка кузова, % (общая и по маркам — мин/среднее);
- `idle`: суммарные часы простоя за отчётную дату (по подразделениям);
- `abc`: число водителей A/B/C.

Это чистый дамп словаря — на отрисовку PDF не влияет, выполняется без сети.

### 2.3 Модуль `explain.py` (новый шаг)

1. Читает `state/last_metrics.json`.
2. Формирует короткий «бриф данных» (плоский текст с цифрами) и системную инструкцию:
   деловой стиль, 3–6 абзацев — что произошло за день, ключевые цифры и динамика
   к прошлому дню, узкие места (низкая загрузка/простои), краткие рекомендации;
   **ничего не выдумывать сверх переданных чисел**.
3. Если `llm.available()` — `llm.ask(brief)`, иначе (или при `RuntimeError`) —
   `_rule_based_note(metrics)`: та же структура, собранная шаблоном из чисел.
4. Сохраняет `output/Пояснительная_записка_<дата>.md` и `state/last_note.txt`.
   Возвращает текст записки (для писем/бота).

Запуск: `python3 explain.py` (самодостаточно, читает state). Идемпотентен.

### 2.4 Размещение записки

- Тело письма: `send_email.py --note "<текст записки>"` (механизм уже есть).
- Подтверждающее сообщение бота: добавить первые ~600 символов записки в текст
  `notify_bot(...)`.
- Файл `output/Пояснительная_записка_<дата>.md` — дополнительное вложение письма
  (расширить `send_email.py`, чтобы помимо xlsx/pdf прикладывать записку, если есть).

**Решение:** записка — отдельный документ, **не** страница внутри PDF. Причины:
PDF остаётся детерминированным и быстрым, сбой/задержка моста не влияет на PDF,
и «пояснительная записка» по смыслу — самостоятельный документ. (Вариант «страницей
в PDF» отклонён как более связанный и медленный.)

## Часть 3. Алерты в Telegram

Канал — админ-чат бота, через `tg_request` (уже есть в `run_daily.py`). Вынести в
хелпер `alert(env, text)`.

### 3.1 Сбои

- `consolidate.py` или `build_pdf.py` завершились с ненулевым кодом → алерт с шагом
  и кодом возврата.
- `fetch` не нашёл свежих вложений / дата отчёта (`last_fetch.meta`) не сегодняшняя →
  алерт «нет свежих данных за <дата>».

Сейчас эти ситуации только логируются — добавляем отправку в Telegram (логи остаются).

### 3.2 Аномалии

Считаются в `explain.py` из `state/last_metrics.json` и сохраняются в
`state/last_alerts.json` — список объектов `{type, text}`. `run_daily.py` после шага
`explain` читает этот файл и прогоняет каждый алерт через `alert()` (с анти-спамом).
Пороги — константы в одном месте (с возможностью переопределить через `.env`):

- `MIN_BODY_UTIL = 95` — средняя загрузка кузова, % (ниже → алерт);
- `MAX_IDLE_H = 1.0` — простои, ч/смену (выше → алерт);
- `MAX_VOLUME_DROP = 30` — падение объёма к прошлому дню, % (больше → алерт).

### 3.3 Анти-спам

При 17 прогонах/день один и тот же алерт не должен повторяться. Файл
`state/alerts_sent.json` — множество ключей `"<дата>|<тип_алерта>"`. Перед отправкой
проверяем ключ; отправляем только новый; после отправки сохраняем. Сброс — естественно
при смене даты (старые ключи можно чистить, оставляя только сегодняшние).

## Критерии готовности

- launchd-задача срабатывает в 6:10…22:10; в логах видны прогоны.
- После прогона существует `output/Пояснительная_записка_<дата>.md`, её текст — в
  теле письма и в сообщении бота; при выключенном мосте записка всё равно формируется
  (правиловый вариант), PDF/XLSX собираются как прежде.
- При искусственном сбое шага и при заведомо аномальных данных приходит ровно один
  алерт в Telegram на каждый уникальный случай за день.
- Письмо уходит только на `alexeimvc@gmail.com`.
